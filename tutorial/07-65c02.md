# Tutorial 7: Switching to the 65C02

[English](07-65c02.md) | [日本語](07-65c02.ja.md) &nbsp;·&nbsp; [← 6. Interrupts](06-interrupts.md)

The 65C02 is the successor of the 6502. It runs the same programs and adds instructions that make them shorter. Glow65 runs as a 6502 by default and as a 65C02 when you ask for it. In this chapter you write one small program twice, once for each CPU, compare their sizes, and then run the 65C02 version on both machines to see what an undefined instruction does. Everything below was run on Glow65 and checked by `Tests/Glow65Tests/TutorialChapter65C02Tests.swift`.

## 1. What the 65C02 adds

This chapter uses four of the new instructions:

| Instruction | Bytes | What it does | The 6502 way |
|---|---|---|---|
| `stz addr` | 2 to 3 | Stores 0 to memory | `lda #$00` first, then `sta addr` |
| `inc a` | 1 | Adds 1 to A | `clc` and `adc #$01` (3 bytes) |
| `bra label` | 2 | Branches always | `jmp label` (3 bytes) |
| `phx` / `plx` | 1 | Pushes / pulls X (`phy` / `ply` for Y) | `txa`, `pha` and `pla`, `tax` (through A) |

The 65C02 also has more addressing modes and a few more instructions (`wai`, `stp` and the bit instructions among them). The details are in the manual: [4.11 Modes Added by the 65C02](../manual/en/04-addressing.md#411-modes-added-by-the-65c02) and [5.7 The 65C02](../manual/en/05-7-65c02.md). How Glow65 implements it is written in [the implementation spec](../documents/specs/2026-10-12-65c02-mode.md).

## 2. The same program twice

Both programs do two things. They clear the 16 bytes at `$03D0-$03DF`, and then they count a 16-bit value from 0 up to `$0300` in `COUNT` (`$03F0` low, `$03F1` high). The count is kept in A (high byte) and in memory (low byte).

[`clear_6502.s`](clear_6502.s) is the version for the 6502:

```
        ldx #$0F        ; X = 15: index of the last byte of the area
        lda #$00        ; a 6502 cannot store a constant: A must hold the 0
clr:    sta BUF,x       ; clear one byte
        dex
        bpl clr         ; repeat until X wraps from 0 to $FF
        sta COUNT       ; A is still 0
loop:   cmp #$03        ; A = high byte of the count: finished?
        beq done
        inc COUNT       ; low byte + 1
        bne loop        ; no wrap: next
        clc             ; the low byte wrapped: high byte + 1
        adc #$01
        jmp loop        ; the 6502 has no unconditional short branch
done:   sta COUNT+1
        rts
```

[`clear_65c02.s`](clear_65c02.s) is the version for the 65C02:

```
        ldx #$0F        ; X = 15: index of the last byte of the area
clr:    stz BUF,x       ; STZ stores a zero without using A
        dex
        bpl clr         ; repeat until X wraps from 0 to $FF
        stz COUNT       ; the low byte of the count
        lda #$00        ; A = high byte of the count
loop:   cmp #$03        ; finished?
        beq done
        inc COUNT       ; low byte + 1
        bne loop        ; no wrap: next
        inc a           ; the low byte wrapped: INC A adds 1 to A
        bra loop        ; BRA: unconditional branch, 2 bytes
done:   sta COUNT+1
        rts
```

The 65C02 version uses `stz` instead of loading a zero into A, `inc a` instead of `clc` and `adc #$01`, and `bra` instead of `jmp`. The loop in the middle is the same.

## 3. Assemble them

`Tools/assemble.sh` needs the `cc65` package, as in the earlier chapters. The 65C02 source begins with `.setcpu "65C02"`, which tells `ca65` to accept the new instructions. Without it, `stz` is an error. The 6502 source has `.setcpu "6502"`.

```bash
Tools/assemble.sh tutorial/clear_6502.s
Tools/assemble.sh tutorial/clear_65c02.s
```

```
tutorial/clear_6502.bin: 32 bytes (load at $0300)
tutorial/clear_65c02.bin: 29 bytes (load at $0300)
```

The 65C02 version is 3 bytes shorter: 2 for `inc a` and 1 for `bra`. `stz` saves nothing in this program, because the 65C02 version still needs its own `lda #$00` for the high byte, while the 6502 version gets by with one. The `.bin` files are committed in `tutorial/`, so you can skip this step.

## 4. Run it on a 65C02

Start Glow65 as a 65C02 and load the 65C02 binary. `--cpu 65c02` works for both programs:

```bash
swift run glow65-cli --cpu 65c02 --load tutorial/clear_65c02.bin@0300
```

or

```bash
swift run Glow65App --cpu 65c02 --load tutorial/clear_65c02.bin@0300
```

In the app, flip POWER up and click the terminal. First fill the area with `$AA`, so you can see it being cleared:

```
E 03D0 AA AA AA AA AA AA AA AA AA AA AA AA AA AA AA AA
```

List the program. The monitor's `L` command detects the CPU at run time, so on a 65C02 it shows the new instructions by name:

```
L 0300 031C
```

```
0300  A2 0F     LDX   #$0F
0302  9E D0 03  STZ   $03D0,X
0305  CA        DEX
0306  10 FA     BPL   $0302
0308  9C F0 03  STZ   $03F0
030B  A9 00     LDA   #$00
030D  C9 03     CMP   #$03
030F  F0 08     BEQ   $0319
0311  EE F0 03  INC   $03F0
0314  D0 F7     BNE   $030D
0316  1A        INC   A
0317  80 F4     BRA   $030D
0319  8D F1 03  STA   $03F1
031C  60        RTS
```

Run it and dump the area and the counter:

```
G 0300
D 03D0 03F1
```

```
03D0: 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
03E0: 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
03F0: 00 03 00 00 00 00 00 00 24 F4 24 F4 00 00 00 00
```

The 16 bytes at `$03D0` are zero again, and `$03F0/$03F1` hold `00 03`, which is `$0300` (low byte first). The bytes at `$03F8-$03FB` are the interrupt vectors of chapter 6.

## 5. Run it on a 6502

Now start the same binary on the default CPU. Leave out `--cpu` (or write `--cpu 6502`):

```bash
swift run glow65-cli --load tutorial/clear_65c02.bin@0300
```

Fill the area with `$AA` again and list the program:

```
E 03D0 AA AA AA AA AA AA AA AA AA AA AA AA AA AA AA AA
L 0300 0318
```

```
0300  A2 0F     LDX   #$0F
0302  9E        .BYTE $9E
0303  D0 03     BNE   $0308
0305  CA        DEX
0306  10 FA     BPL   $0302
0308  9C        .BYTE $9C
0309  F0 03     BEQ   $030E
030B  A9 00     LDA   #$00
030D  C9 03     CMP   #$03
030F  F0 08     BEQ   $0319
0311  EE F0 03  INC   $03F0
0314  D0 F7     BNE   $030D
0316  1A        .BYTE $1A
0317  80        .BYTE $80
0318  F4        .BYTE $F4
```

The bytes are the same, but the 6502 does not know `$9E`, `$9C`, `$1A` and `$80`, and `L` prints them as `.BYTE`. The 6502 in Glow65 runs such an undefined opcode as a one-byte NOP (2 cycles). The bytes after it, which were the operands of `stz` and `bra`, are then read as instructions of their own: `D0 03` becomes a `BNE`, `F0 03` a `BEQ`. Run it:

```
G 0300
D 03D0 03F1
```

```
03D0: AA AA AA AA AA AA AA AA AA AA AA AA AA AA AA AA
03E0: 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
03F0: 00 00 00 00 00 00 00 00 24 F4 24 F4 00 00 00 00
```

Nothing was cleared: the area still holds `$AA`. The counter is `00 00` instead of `00 03`. `inc a` is a NOP here, so A never reaches 3: the low byte counts through 256 values once and the program falls out of the loop with A still 0. The program did not crash and did not print an error. It ran to the end and returned to the monitor with the wrong answer. This is why a 65C02 program must not be loaded on a 6502 machine unless you want to see this. The CPU does not warn you.

The other direction is harmless. The 6502 program uses only instructions the 65C02 also has, so `clear_6502.bin` produces the same dump on both machines:

```
03D0: 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
03E0: 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
03F0: 00 03 00 00 00 00 00 00 24 F4 24 F4 00 00 00 00
```

For reference, `L 0300 031F` on `clear_6502.bin` prints 6502 instructions only, and it prints the same lines on either CPU:

```
0300  A2 0F     LDX   #$0F
0302  A9 00     LDA   #$00
0304  9D D0 03  STA   $03D0,X
0307  CA        DEX
0308  10 FA     BPL   $0304
030A  8D F0 03  STA   $03F0
030D  C9 03     CMP   #$03
030F  F0 0B     BEQ   $031C
0311  EE F0 03  INC   $03F0
0314  D0 F7     BNE   $030D
0316  18        CLC
0317  69 01     ADC   #$01
0319  4C 0D 03  JMP   $030D
031C  8D F1 03  STA   $03F1
031F  60        RTS
```

## 6. The CPU switch on the panel

In the app, the **CPU** switch on the panel chooses between the 6502 and the 65C02. It works only while POWER is off, and the `--cpu` option chooses the CPU at start. To change the CPU, turn POWER off, move the switch, and turn POWER on again. Powering on clears RAM, so load the program after POWER is on: `--load` does it every time, or use **File → Load Program…**, or type the bytes.

## 7. Things to try

1. **Another limit.** On the 65C02 machine, change the `cmp` operand with `E 030E 01` and run `G 0300` again. The counter stops at `$0100`: the row printed by `D 03F0 03F1` starts with `00 01`.
2. **Push X.** Enter `E 0300 A2 07 DA A2 00 FA 8E F0 03 60`. The program is `ldx #$07`, `phx`, `ldx #$00`, `plx`, `stx $03F0`, `rts`. Run it with `G 0300` and look at `D 03F0 03F0`. On a 65C02 the first byte is `07`: `plx` brought the 7 back. On a 6502 it is `00`, because `phx` and `plx` do nothing there.
3. **Write your own.** Use `dec a` and `bra` to count down from 10 in A, and store the 0 at the end with `stz`.

## 8. Things to remember

- The 65C02 runs all 6502 programs, and adds instructions such as `stz`, `inc a`, `bra`, `phx` and `plx`.
- Tell `ca65` which CPU you mean with `.setcpu "6502"` or `.setcpu "65C02"`.
- On a 6502, the new opcodes are undefined. Glow65 runs them as NOPs, so a 65C02 program gives wrong results without any error.
- `L` shows `STZ`, `BRA` and the other new instructions by name only on a 65C02 machine. On a 6502 it prints them as `.BYTE`.
- The CPU can be changed only while POWER is off.
